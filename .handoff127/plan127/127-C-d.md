## What the skipper sees

At the dock, after the 127 build is on his phone:

1. **He installs once and types one code.** One install on the Pi takes about 10 minutes, most of
   it the Pi opening every chart once in memory to list it. The install prints a one-time code.
   He types it on his phone: Settings → Boat network → Boat Pi → **Charts from Serene Summer**.
   The row then reads "This iPhone is set up · 1,025 charts on Serene Summer, opened in the Pi's
   memory only". The numbers are the Pi's own. The boat name comes from the pairing, never from
   the code.
2. **He checks it, then purges.** After a five-minute check (open the chart list, open a chart at
   Airlie), he runs one more command, `purge.sh`. It deletes the Pi's old decrypted chart files
   (the live store, about 1.1 GB, plus any orphans and staging the ocharts-audit B7 step has not
   already removed). This is the last unencrypted copy on any medium. From then on the only chart files
   on the boat are the encrypted sets o-charts delivered.
3. **Charts look exactly as before.** He uses Plan Your Day, Auto and the chart as he does today.
   Cells come from the Pi over the boat's Wi-Fi, and the phone keeps them in memory (127-C-c).
   The first open after the Pi restarts takes a few seconds longer while the Pi opens those cells.
   After that they come from the Pi's memory.
4. **The watch never stutters for charts.** Opening charts runs in its own low-priority process,
   held to two of the Pi's four cores. That process is the one the kernel stops first if memory
   runs short. Nothing that opens or reads a chart runs inside the anchor-watch, night-watch,
   alarm-relay or telemetry process any more.
5. **When the Pi says no, the app says why, in plain words:**
   - On the tailnet from home: "Charts come over Serene Summer's own Wi-Fi. Join it to get charts."
   - With the dongle out: "Serene Summer can't open her charts. Check the o-charts dongle is
     plugged into the Pi."
   - A sixth device: "Five phones and tablets already get Serene Summer's charts. Remove one to add
     this one."
6. **Adding the iPad.** On the set-up phone he taps "Code for another phone or tablet" and types
   that code on the iPad. Up to five devices. "Remove" on any of them takes one away again.
7. **A new o-charts edition.** He pastes the download link as today. The Pi keeps the set
   encrypted and opens cells from it as they are needed. Nothing decrypted is written. (If this
   piece is cut, the link answers "New chart sets install in the next update. Your charts keep
   working.")
8. **Nothing changes in routing.** Routing stays on the phone (127-PYD-2, Auto). The Pi's own
   route endpoint answers "Routing runs on your phone in this build" (nothing in the app calls it).

## Decisions (our recommendation, on the standing order)

1. **The vault is its own process, `thalassa-chart-vault`, with its own systemd unit.**
   - It is the only thing on the Pi that turns a delivered `.oesu` into chart data. It does that in
     its own RAM, on demand.
   - It talks to thalassa-cache over a unix socket (`/run/thalassa-chart-vault/vault.sock`, 0600,
     same user) and nothing else. It opens no network socket at all (decision 3).
   - thalassa-cache stays the front door: pinned TLS, device token, LAN check and signing. It
     streams the vault's bytes straight through and never parses, hashes or holds a whole cell.
     The vault hands it the hash it already checked, so nothing CPU-bound about charts ever runs
     in the watch's thread.
   - In 128-129 the same process becomes the brain (routing, answers). The name and the socket
     protocol are versioned (`/v1/...`) for that.
2. **The unit limits.** Values are provisional; measurement M sets the final ones.

   ```ini
   [Unit]
   Description=Thalassa chart vault (o-charts cells decrypted in memory only)
   After=local-fs.target
   StartLimitIntervalSec=600
   StartLimitBurst=5
   [Service]
   Type=simple
   User=<thalassa-cache's User, filled in at install>
   WorkingDirectory=/opt/thalassa-pi-cache
   ExecStart=<thalassa-cache's node binary> --max-old-space-size=512 dist/vault/main.js
   Environment=NODE_ENV=production TMPDIR=/tmp VAULT_LRU_MB=600
   Nice=10                 # thalassa-cache runs at Nice=-5: ~28x the CPU weight
   CPUQuota=200%           # two of four cores at most; the watch, Signal K and the rest keep two
   IOSchedulingClass=best-effort
   IOSchedulingPriority=7
   MemoryHigh=1400M
   MemoryMax=1700M
   MemorySwapMax=0         # the vault's pages are never swapped, to zram or anywhere
   OOMScoreAdjust=800      # the kernel kills the vault first, never the watch
   LimitCORE=0             # no core dump of chart memory (oexserverd inherits it)
   UMask=0077
   PrivateTmp=yes          # oexserverd's FIFOs live in the vault's own tmpfs /tmp
   NoNewPrivileges=yes
   ProtectSystem=strict
   ProtectHome=read-only
   ReadWritePaths=/opt/thalassa-pi-cache/enc-charts/vault
   RuntimeDirectory=thalassa-chart-vault
   RuntimeDirectoryMode=0700
   RestrictAddressFamilies=AF_UNIX
   PrivateNetwork=yes      # only if M1 shows oexserverd opens no network socket
   KillMode=control-group
   Restart=on-failure
   RestartSec=30
   TasksMax=64
   [Install]
   WantedBy=multi-user.target
   ```

   `PrivateDevices` stays off, because the SG-Lock needs `/dev/bus/usb`. `MemoryDenyWriteExecute`
   stays off, because V8's JIT needs it. Inline `#` comments are for this plan only; systemd does
   not allow trailing comments, so the real file puts each one on its own line.
3. **Network isolation is measured, not assumed.** M1 records which files and sockets `oexserverd`
   opens while it decrypts.
   - **If it only reads the delivered set and its library and uses AF_UNIX/FIFOs:**
     `PrivateNetwork=yes` and `ProtectHome=read-only` ship. That gives Roberto a strong sentence:
     the process that holds decrypted charts has no network at all.
   - **If it writes anywhere** (a log in `~/.opencpn`, say): that one path goes in `ReadWritePaths`,
     and the README names it. We stop and report if what it writes is chart data.
   - **USB and netlink (critic pass 2).** The SG-Lock is reached through libusb, which may open an
     `AF_NETLINK` socket for hotplug. `RestrictAddressFamilies=AF_UNIX` would make that fail, and
     `PrivateNetwork=yes` puts the vault in a namespace that may not see USB uevents. M1 therefore
     also lists netlink sockets (`ss -0ap`, or the `socket:[…]` inodes against `/proc/net/netlink`);
     if oexserverd or libsglarm64 opens one, the unit allows `AF_UNIX AF_NETLINK`. The install
     smoke adds one dongle check: the vault decodes a cell after `systemctl restart
     thalassa-chart-vault` (dongle left in), and the README says to restart the vault after any
     re-plug until a re-plug has been tested.
4. **C2, the front door.** Every `/api/enc` route gets one router-level middleware with three
   checks, in order:
   1. **`Cache-Control: no-store` and `Pragma: no-cache`** on every response, errors included.
   2. **Boat LAN only.** The peer address must be IPv4 and inside a subnet of a non-tailscale,
      non-loopback interface (`os.networkInterfaces()`). It must not be that interface's default
      gateway (`/proc/net/route`), must not be in 100.64.0.0/10, must not be loopback, and must
      not be IPv6. `X-Forwarded-For` is never trusted.
      - Refusing the gateway closes the RUTX50's subnet route: a tailnet device routed through
        the router arrives as the router.
      - Refusing loopback closes a future `tailscale serve`.
      - The server binds 0.0.0.0, so IPv6 cannot connect anyway.
      - Refused: `403 {code:'charts-boat-wifi-only'}`.
   3. **Device token.** The header `X-Thalassa-Chart-Device: <43-char base64url>` must be a
      registered device, compared by SHA-256 with `timingSafeEqual`. Without it the answer is
      `401 {code:'chart-device-not-enrolled'}`; a removed device gets `'chart-device-removed'`.
   - The only routes without a token are `POST /api/enc/devices/enrol` (it takes a code, and is
     still LAN-only and rate-limited) and `GET /api/enc/devices/status` (enrolled or not, no data).
   - This applies to every route, `/health` and `/ocharts/setup` included, because the vision says
     every route. The test enumerates the router stack itself, never a list (memory
     thalassa-pi-pinned-transport: "A guard against 'someone forgot a call site' cannot be a list
     of the sites someone remembered").
5. **Enrolment by code. At most 5 devices. Nothing secret is stored in the clear.**
   - **Codes.** A code is 10 Crockford base32 characters (50 bits) and lasts 15 minutes; at most 3
     are pending at once. The Pi keeps only a SHA-256 of each, in `enc-devices.json` (0600,
     CACHE_DIR).
   - **The first code** is printed by `install.sh` from `node dist/vault/enrolCode.js`, which Shane
     can also run over ssh later.
   - **Later codes** come from `POST /api/enc/devices/code` on an enrolled device.
   - **Enrolling.** `POST /api/enc/devices/enrol {code, label}` returns `{deviceId, token}`. The
     token is 32 random bytes; the Pi stores its SHA-256 and the label.
   - **Limits.** A sixth device gets `409 'chart-device-limit'`. After 5 wrong codes in 10 minutes
     from one address, or 20 in an hour overall, the answer is `429 'chart-code-tries'`.
   - **Managing devices.** `GET /api/enc/devices` lists label, enrolled and last seen.
     `DELETE /api/enc/devices/:id` removes one, and a device can remove itself.
   - **On the phone,** the token lives in the Keychain (new allowlisted key
     `thalassa-pi-chart-device`, `ThisDeviceOnly`, never in iCloud or backups). It is bound to the
     pairing's `deviceId`, cached in memory after one read per launch (memory capacitor-bridge-queue:
     one serial plugin queue), and dropped on `forgetPairing` or on a `chart-device-removed` answer.
     It is never put in a URL, a log line or localStorage.
6. **The index comes from the delivered sets. The 2 GB store goes.**
   - **What it reads.** The vault scans `ENC_WATCH_DIR` (`~/Charts`) and `enc-charts/sources/*` for
     o-charts sets, using the same shape rules as `inspectOChartsSets`: exactly one key XML per
     set, every `.oesu` keyed.
   - **First pass.** It opens each `.oesu` once in RAM (decrypt → parse → emit → hash → drop) to
     learn its catalogue fields.
   - **The file it writes,** `enc-charts/vault/vault-index.json` (0600), holds ONLY: cellId,
     native id, producer, edition, update, issued date, the cell's coverage rectangle, feature
     count, served size, contentSha256, the parser schema, set dir + file name, the encrypted
     file's SHA-256, and `licence:'protected'`. It holds no feature, depth, position inside the
     cell, name or picture.
     - A test enforces this with a key allowlist and a scan for feature content.
     - OpenCPN's chart database keeps each chart's extent in the same way. (A "tell" line for
       Roberto: question 3.)
   - **Restarts.** A restart reuses the index and re-opens only files whose encrypted hash changed.
     A new parser schema re-indexes everything once, in RAM.
   - **When the same cell is in two sets,** the newest (edition, update, issued) wins: the same
     order as `compareChartRevision`.
   - **Cells the skipper removed** are held in `removed.json` (ids only). A new delivery that
     contains the cell brings it back; a restart never does.
   - **Open cells** move to `enc-charts/open/` with their own index and `licence:'open'`. Writing
     open data to disk is allowed. **"Open" is 127-C-b's fail-closed classifier, nothing wider
     (critic pass 2):** a NOAA id with a US producer (today only US5GA22M). An unencrypted S-57 the
     skipper uploads or links that the classifier calls protected (any non-NOAA id) is NOT written:
     the conversion answers `415 {code:'not-open-chart'}` with "Thalassa keeps only open charts (NOAA)
     as files on the Pi. Open other charts in OpenCPN." (127-C-c's wording family). The earlier "any
     unencrypted S-57 the skipper converts → open" contradicted C-b and the vision's "protected by
     default".
7. **The cache is RAM only, bounded and fair to the watch.**
   - **The LRU** holds Buffers, not JS strings: a string that meets one non-Latin-1 character
     doubles in V8. It is capped by bytes (`VAULT_LRU_MB`, 600) and keyed by
     `cellId@contentSha256`.
   - **Decodes are serial.** The FIFO protocol is one cell at a time. Concurrent requests for the
     same cell share one decode (single-flight).
   - **Order:** a phone's request first, then prewarm, then indexing. A queue over 64 answers
     `503 'vault-busy'` with `Retry-After`.
   - **Prewarm** fills at most 60% of the LRU. It uses a position hint from thalassa-cache (its
     current fix, every 10 minutes) and opens the cells within 30 NM of the boat, finest scale first.
   - **Checks on every decode.** The hash must equal the index. If it does not, the vault re-indexes
     that cell and the phone re-syncs, because its `expectedSha256` check refuses the old hash.
   - **Logging.** The vault logs only cell ids, counts and milliseconds, never content (the journal
     is persistent: pi.md).
8. **The parser comes into pi-cache as a generated mirror** (the router-engine pattern):
   - `pi-cache/scripts/sync-senc-engine.mjs` copies the needed extractor modules into
     `pi-cache/src/sencEngine/`:
     - featureParser, geojsonEmitter, binaryReader, recordTypes, s57Classes, s57Attributes;
     - mercator, meshOutline, keyFile, chartProvenance, oexserverd.
   - It writes a `syncedFrom.ts` stamp and has a `--check` mode, wired into CI beside the two mirror
     checks (`.github/workflows/ci.yml:92-102`).
   - Two edits ride the mirror and are applied upstream first. The CSV reference directory is
     injected rather than resolved beside the module, and the command FIFO path can be overridden
     (`VAULT_OEX_COMMAND_PIPE`), so tests can run a fake daemon.
   - **No dependency change:** no npm ci, no better-sqlite3 rebuild.
   - The install copies the two catalogue CSVs from the Pi's own `~/thalassa-marine-weather/
     tools/senc-extractor/reference/` into `/opt/thalassa-pi-cache/reference/`, checked against the
     hashes the pre-check read. The vault then no longer depends on that older checkout (126-05
     risk: "local senc-extractor edits").
9. **Routing on the Pi is off.** `/route` and `/route-prepped` answer
   `503 {code:'routing-on-phone', error:'Routing runs on your phone in this build.'}`.
   `routes/enc.ts` drops its `routeInshore` import, so the watch process no longer even loads the
   engine. The engine mirror stays in the tree for 128's brain. The workload lane is left alone.
10. **DELETE really deletes.**
    - **Open cells:** under the index lock, the cell's line goes and every file named exactly
      `cells/<safeId>-<64 hex>.json` or `cells/<safeId>.json` is unlinked. A prefix of another
      cell's id never matches.
    - **Protected cells:** the cell goes into `removed.json` and is evicted from RAM. The encrypted
      `.oesu` stays: it is the licensed delivery.
11. **o-charts installs keep the set encrypted.** `installOChartsDelivery` skips
    `convertAndVerifyOChartsSets`. It verifies the set's shape, retains it in `enc-charts/sources/`
    (as now), calls the vault's `POST /v1/rescan`, and reports new, updated and unchanged from the
    vault's index.
    - pi-cache never spawns `decryptBatch` again. A test spies on `spawn`.
    - **A rescan or re-index never runs during a watch (critic pass 2).** A new set is ~930 cold
      decodes (3-6 min on two cores). While the anchor watch or an armed night watch is on (the
      same loopback check install.sh uses), the vault queues the rescan and says "New charts open
      in memory after the watch"; a phone's own cell request is still served (one decode, at
      Nice 10 inside the quota). The same rule holds for a parser-schema re-index after a restart.
    - `encWatcher`'s `.oesu` branch and `startSourceReconvert` become no-ops for o-charts sets, and
      the vault takes over their job in RAM.
    - **Today's switches stay exactly as set (all `false`).** Nothing in this update reads them to
      start anything new, and nothing can write a decrypted cell whatever they say.
    - **Cut fallback:** `install-from-url` for an `.oesu` archive answers
      `503 'installs-paused'`, and no plaintext path remains either way.
12. **Startup sweep.** At start, thalassa-cache removes every leftover under `TEMP_ROOT` (and
    `thalassa-enc-persist-*`) in its TMPDIR, because the jobs Map is empty then. The `90-enc-staging`
    TMPDIR drop-in stays for encrypted downloads and open S-57. The vault overrides it with

  A current-edition re-download from o-charts brings any back, encrypted.
- **The first index pass takes about 3-6 minutes** (≈1,960 decodes on two cores). During it,
  `/installed` answers `vault-starting`, and the README says to wait. A crash restart reuses the
  persisted index in seconds.
- **The vault's memory squeezes the watch.** The safeguards are `MemoryMax`, `OOMScoreAdjust=800`,
  `MemorySwapMax=0` and M5's numbers. thalassa-cache is unchanged apart from `LimitCORE=0`.
- **Two `oexserverd` processes on one dongle** (OpenCPN over VNC on the Pi at the same time). The
  vault's private `/tmp` keeps the FIFOs apart, but whether the dongle tolerates two daemons is
  unknown. The README says "don't run OpenCPN's o-charts plugin on the Pi while the vault runs"
  until it has been tested.
- **The CSV reference files go missing from the old checkout** (`git clean -fdx`). Since the
  install copies them into `/opt/thalassa-pi-cache/reference/`, that no longer matters.
- **Never run the Pi's `redeploy.sh`,** and never `signalk-server --version` (memory
  pi-calypso-access). Install only this folder.
