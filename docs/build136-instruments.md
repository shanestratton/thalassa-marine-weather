# Build 136 instrument panel, current and performance

Source checkpoint for roadmap 136-01/02/03. This is not a Pi installation or TestFlight/device acceptance receipt. The sensor contract is documented in [instrument evidence](build136-instrument-evidence.md).

## Behavior

- The Instrument Panel has an instrument-derived Current section: drift in knots, set towards true north, original source UTC/time age, explicit leeway provenance or an uncorrected warning. Zero/negligible drift does not acquire an invented direction. A cloud copy is labelled and never supplies the Obs arrow or current correction.
- A source-free current arrow/label sits at the qualified boat position on Obs, independently of modelled current. Its label stays inside the viewport and rotates true set with the camera. Modelled current sources/layers are never changed. It retires on stale/missing position/current, account/feed retirement or leaving Obs. No phone position fallback is used.
- Explicit Recent Pi current history reads at most one 500-point page from a two-hour window over the existing paired TLS transport. The adapter evaluates each historical vector at its row time using separate original sensor clocks. Legacy/unqualified points are counted unavailable; truncated windows are labelled partial. Only the last 20 qualified entries of the returned batch are shown, with no claim that a partial batch contains the newest part of a long window. It is memory-only, aborts on close/account change and makes no WAN fallback.
- Preferences stores per-device, account-scoped hide choices, an optional HUD performance line and local Obs layline toggle. No-data sections disappear; any hidden section remains in its fixed position when re-enabled. If all sections disappear, the device clock remains. Existing relative order is preserved: Clock, Watch, Wind, Barometer, Position, Speed, then new Performance/Current, Depth, Sea temp, Heading, Helm. The actual last visible section owns the full snap height. There is no reordering/named layout. Existing serene helm advice is unchanged.
- Performance uses `useRoutingPolar`/the same resolved polar as routing, retaining source label, selection/scaling and default/learned status. Targets are estimates. VMG is signed water-speed VMG towards true wind; STW is never replaced by SOG. Missing STW leaves measured figures unavailable. Wind outside the polar's actual axis is refused. Actual/polar percentage requires explicit Under sail confirmation and uses measured STW. No RPM or zero RPM does not establish sail. Positive qualified RPM suppresses performance and clears confirmation; source/lane/account change also clears it. A subsequent zero cannot restore that confirmation. Motorboats do not get this section. The existing generic point-of-sail geometry supplies the live label; forecast meteogram remains a separately labelled forecast consumer.
- Obs layline guides use explicit waypoints/destination on the followed route, not generated route vertices. They require known under-sail state, qualified true wind and a mark within 5 nm. Unknown/ambiguous/off-route marks are refused. Local current correction requires matching boat identity and simultaneous live current. The UTC sample time and local-current assumption are shown; absent correction says uncorrected. They neither alter a route nor issue steering/alarm/autopilot commands. Missing heel is never converted into guessed leeway; only explicit source-qualified signed leeway can be used.
