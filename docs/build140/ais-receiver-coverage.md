# 140-05 AIS receiver coverage and Pi fleet sharing — source checkpoints

This work is staged only. No service control, worker route, Pi installation, raw reader, forwarding timer, provider licence or Buddy watch has been activated. The complete 135 AIS schema, bounded writer and separately reviewed transport/display rights remain prerequisites. The old phone sharing flag does not authorize a Pi. Internet AIS and these coverage cells do not enter local CPA or alarm stores.

The wire and worker core require a separate current Pi consent revision, exact owner/vessel/relay/Pi/controller/enrollment/source binding, fresh P-256 signed payload, actual enabled scoped relay and atomic SQL admission. The Pi uses its existing pairing identity; it never receives a service-role key or user session. Consent acknowledgements are HMAC-bound to the existing scoped relay credential and exact one-use proposal nonce. Pairing is the existing first-use trust decision, not hardware attestation or proof that three owners are three different people. The actual Pi enrolled-controller/source checks, phone review, HTTP endpoints and coverage layer are now staged in source.

`20261017011825_ais_receiver_coverage.sql` keeps one private current coarse cell per receiver/vessel, one current consent, and at most 16 boot replay positions per consent. New consents are capped 4096, with a shared row lock preventing capacity races. No traffic or receiver position history is stored here. Batch admission costs four writes against the existing persisted hourly/daily AIS budget before changing private replay or coverage state; subsequent shared-vessel writes still use the existing bounded writer. Disabled, transferred, archived, revoked, expired or superseded policy cannot admit a batch. Withdrawal works even while fleet rights/control are held and erases that receiver's coarse cell and replay rows.

Coverage comes only from a freshly decoded actual AIVDM observation together with a separately fresh measured receiver fix reduced aboard to a fixed 2° cell. AIVDO alone, provider poll receipts and an ownship GPS fix never qualify as receiver evidence. A cell needs at least three distinct current owner accounts and Pi IDs; its receiver observations must remain in that cell for five minutes before first publication. A move or observation lapse restarts that delay. Last original observations expire after ten minutes. This is coarse recent listening evidence, not a live receiver location or a promise that a target will be received.

The authenticated read RPC returns at most 256 cell IDs, a global rounded/delayed `asOf`, short response expiry and explicit partial/held state. It returns no receiver identities, contributor count, exact coordinates or per-cell timestamps. PostGIS checks the actual fixed cell boxes, including dateline windows. Both new controls default OFF and separately require reviewed transport/display references; no rights are inferred from a configured provider key.

It opens only the explicitly declared loopback Signal K receiver rebroadcast, with byte/line/rate bounds; it never opens the scarce hardware gateway.
