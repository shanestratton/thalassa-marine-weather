## Identity and consent

- At most ten contacts per account, across boats. Private tables have RLS and no direct `anon`/`authenticated` read or write grants; owner RPCs expose only that caller's current owned, unarchived boat. There are no recipient hashes, chat IDs, tokens or provider responses in owner summaries.
- `configure_shore_contact(boat, contact|null, expectedRevision|null, configuration|null)` is explicit CAS. New contacts start off; deleting needs the existing revision. Recipient, channel, label or position-permission changes retire old consent, nonces and pending deliveries. A confirmed contact requires a separate owner enable. A stale edit is never retried.
- Email invitations use random 256-bit confirmation nonces, hashed in the database, one use and 24-hour expiry. The separate recipient revocation token is HMAC-SHA256 with its own server-only key, hashed in the database, one use and one-year expiry. Owner on/off revisions preserve the original revocation token. Email workers verify the reconstructed HMAC against the stored hash before sending, so a key mismatch fails closed.
- Confirmation/revocation links carry the bearer **only in the URL fragment**. The dependency-free `services/shoreConsentLink.ts` import executes before Sentry/app bootstrap. It retains native `History.replaceState` before telemetry can wrap it, removes recognized initial/same-tab fragments, and suppresses the raw recognized `hashchange` event. A nonce stays in RAM and is redacted after success or dropped on dismissal. Unrelated hashes are unchanged. Link GET/scanners do not record consent; an explicit recipient POST is required.
- Telegram invitations are deliberately shareable private invitation links, not verified usernames. A fresh `/start <nonce>` previews the fixed anchor-notice and position-sharing policy, without consent. The nonce is pinned to that stable numeric private chat/user pair and current contact revision. Only the explicit inline confirmation on this bot's own private message may consume it; the preview expires after five minutes, and another chat cannot replace it. Callback data uses canonical base64url for the 32-byte nonce (57 bytes including its fixed prefix, below Telegram's 64-byte cap). Groups, channels, bot senders and mismatched IDs are refused. The owner must verify the intended person received their private link. Changing the configured bot invalidates admission of old consent.
- `/stop` revokes that private recipient's contacts and pending work, including while normal messaging is paused. It can honor an older original command if its update ID is newer than the retained high-water mark; revocation never fabricates a fresh sensor report. `/where` and previews require original message clocks within five minutes; confirmation requires the original bot prompt clock and database preview within five minutes. Callback acknowledgement is fixed text and is never consent evidence. Duplicate updates do not send again. There is no arbitrary message or Signal K path surface.

## Exact boat/source boundaries

Pi anchor events use `pi_diary_relays.boat_id`, current relay owner/enabled state and the exact current anchor session. Phone sessions lack a boat column: `bind_shore_anchor(boat, session, expectedRevision)` deliberately registers a current owned `vessel`-role phone watch. A new session needs deliberate binding; an existing session cannot be relabelled to another hull. No active-vessel preference or account-level Guardian position is inferred.

Every provider attempt rechecks current owned boat, contact revision/consent/enabled state, source capability and unresolved current incident. Phone drag facts expire at 120 seconds; stopped phone watches and retired vessel roles refuse. Pi drag/GPS state needs a heartbeat within 35 seconds; missing contact and expiring lease have distinct fixed wording. These notices report an alarm keeper's state, not a verified live position.

`/where` additionally needs per-contact owner position permission and exactly one eligible shared vessel. It pins the explicit weather-position registration revision and consumes only `private_weather_watch.weather_position_current(boat)` original-clock receipts, at most fifteen minutes old. New source registration, stale/missing receipt, transferred/archived hull or ambiguous eligible vessels return unavailable. No account-selected or phone-position fallback exists. The optional weather position migrations/source/publisher remain separate activation prerequisites; missing capability stays closed.

## Bounded delivery and truthful readiness

- Separate UTC budgets: ten invitations and thirty provider attempts per owner/day; global five-hundred invitations and five-thousand attempts/day; ten-minute invitation cooldown. These caps are independent of AIS/anchor push quotas.
- Incident/contact uniqueness prevents reminder fan-out duplicates. Pending rows expire at ten minutes; audit/dedupe rows are retained for seven days. Telegram high-water marks are bounded to known recipients and pruned after a day. Expired session bindings and old global quota rows are pruned.
- Work scans at most four pages of twenty candidate events and claims at most ten deliveries, with a twelve-second work budget between bounded operations. HTTP operations have five-second aborts, no redirects and body caps (4 KiB incoming app, 8 KiB webhook, 16 KiB provider, 64 KiB fixed database response). At or above eighty candidate events/full ten-delivery batches, it cannot certify a complete pass; readiness remains unavailable until a complete healthy run. This is not a coverage guarantee or a global throughput benchmark.
- Email retries at most three times under the same fixed Resend idempotency key/body. Telegram has no equivalent idempotent-send contract: its single attempt is reserved before HTTP. An uncertain outcome is terminal rather than automatically duplicated. Provider acceptance is not recipient delivery/read evidence.
- A last database guard immediately precedes HTTP. A provider may accept just before a concurrent revocation commits; distributed atomic recall is not claimed.
- A fresh list, explicit deployment versions, reviewed entitlement lease, exact active cron command and a complete healthy worker tick within fifteen minutes are all needed for the UI's ready flags. Mere SQL presence enables nothing. Existing contacts can still be stopped/removed when provider capability is held; new opt-ins stay hidden until capability exists. Account replacement hides private rows/drafts and rejects late invitations. Satellite Mode prevents contact list/write/invite WAN, including explicit attempts.
