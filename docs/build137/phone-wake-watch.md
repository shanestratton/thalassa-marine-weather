# Foreground wake-rule watch and Pi handoff

The saved eight presets now evaluate on the phone while the app is active. Discovery reads the paired Pi's fixed sensor catalogue and original readings over pinned native TLS on the boat LAN. Enrollment and current account, pairing, Pi key, vessel profile and confirmed draft fence every request and delayed result. Direct Signal K gauges, cloud rows and phone location do not qualify a source.

Saving the editor changes only the account's phone preferences. `Keep saved rules on Pi` is an explicit bounded compare-and-swap request; replacing an existing Pi configuration also requires the visible replacement checkbox. A successful write acknowledgement is not running proof. Only update 7's fresh exact owner/feed/rules/configuration/instance proof qualifies the keeper label, and every enabled source expires by its own original clock, including the shorter depth/wind/engine windows. Locked-phone delivery remains unavailable in this checkpoint.

Unknown, stale and repeated measurements cannot clear an active alarm. Quiet hours and episode silence release only this watch's audio lease. A late audio acquisition after retirement releases that exact lease. Anchor and collision/distress owners retain their own leases; wake-depth cards precede the remaining custom presets in the existing alarm stack.

Boot and foreground resume read only already-enabled phone rules. Backgrounding stops phone transport and its owned sound. Account, pairing or vessel retirement clears its source catalogue and evidence. No phone path automatically arms, replaces or clears Pi rules, retries a mutation, or falls back to the WAN. A failed/conflicting edit preserves the existing Pi watch; another currently enrolled phone of the same owner/boat can deliberately replace or clear the exact current revision. A changed vessel's saved configuration is review information and cannot become running proof for the new feed.

The server mounts all four wake endpoints behind the app API and their independent physical-LAN/enrollment door, including observe mode. The shared JSON parser leaves this prefix untouched so the feature parser can authenticate first and enforce its own 16 KiB uncompressed raw-wire cap. `draftM=none` explicitly avoids inheriting a saved Pi draft when the phone has no confirmed draft. Ordinary application JSON parsing remains before the command lock.

Validation at this source checkpoint: the combined phone/editor/model/bootstrap/alarm regression run passed 105 tests; the later cross-phone controller run passed 27. The actual mounted Pi routes/store/catalogue/runner checks passed 24 with one explicit Windows symlink-permission skip, and the wider route-table run had only the two unchanged Windows mode-bit failures. The Pi compiler passed. The full app compiler passed before the narrow cross-phone follow-up; final combined compilation and Linux security assertions remain release gates. Mobile WebKit passed all three 300/375 px, 130% text, keyboard and explicit-Save cases after integration. Chromium uses the installed Chrome channel in the external local proof configuration; the default cache lacked its headless binary, which is an environment failure rather than an app assertion.

No Pi installation, database migration, Edge deployment, Apple upload or physical locked-phone acceptance is implied by these source checks.
