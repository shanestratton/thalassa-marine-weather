# 137-06 · Float-plan overdue watch — prepared, held

This adds one explicit overdue watch per owned vessel, compact-plan review in the existing Float Plan, and owner-first / consenting-personal-contact escalation. **No migration, function, cron, provider, message or rescue integration is activated.** The retired public `float-plan` function stays a 410 tombstone. The full private float plan still uses its existing manual share/export paths.

## Boundaries and consent

- Only the reviewed vessel label, departure/destination labels, departure/ETA/overdue UTC milliseconds and person count are saved. No roster, medical notes, birthdays, equipment, credentials, raw waypoints, chart/routing evidence or public tracking handle is uploaded. The separate compact mapping is literal; the full FloatPlanInput is never serialized by this feature.
- New watches default off. Owner RPCs require the exact currently owned/unarchived boat and revision CAS. At most five active watches per owner. Arrival and cancellation are explicit owner actions; extension/replacement retires the previous revision and pending work. GPS motion never implies arrival. A still-open Float Plan keeps its opening account/boat binding, including across lazy loading; switching either requires reopening/reviewing it. Closing it prevents late save completions from starting background reloads.
- Legacy 137-05 contact configurations remain anchor-only. Optional `allowOverdue:true` changes the permission purpose, retires prior consent and pauses the contact. A new version 2 invitation and explicit recipient confirmation are mandatory. Legacy invitation/confirmation callers default to 1 and cannot authorize overdue permissions. Email and private Telegram prompts state the exact purpose and position choice. Link GET, `/start` and scanners never record consent. Confirmed contacts still need a separate owner enable, and the watch independently pins each selected contact revision.
- Removing overdue permission pauses the contact and requires renewed anchor-only consent. `/stop` and existing revocation links also invalidate overdue provider guards. No Telegram username/group authority exists. Email capability is independent of an absent Telegram account; no bot is provisioned here.
- Position sharing requires both owner and recipient permission, pinned to the explicit vessel/relay/source registration. There is no account Guardian, active-boat, phone GPS or guessed source fallback. The optional fixed private lookup reads only the matching current registration/relay/owner. Last reports are at most 24 hours old when a notice is prepared and retain their original UTC measurement time. Missing/future/expired reports remain unavailable. A changed registration retires the old watch's admission; a stale fix on the same registered source does not become fresh or prevent a notice without a position. Such reports are for a human reviewing an overdue plan, never navigation or live tracking.

## Owner first, then a real grace period

`overdue_watch_work` queues a distinct ordinary `overdue_notice` first. Queue insertion and generic preflight **never** start grace. A real registered iOS owner token is required to arm; if no real owner attempt can be initiated later, the watch remains awaiting that attempt and contacts are not escalated automatically.

The separately prepared sender helper is `supabase/functions/send-push/overdue-delivery.ts`, exporting `createOverdueDeliveryGuards(queueId,data,read,attempt,now?)`:

1. `current()` is read-only preflight through service-only `overdue_owner_current(queueId)`.
2. `beforeHttp()` must run after a real target, JWT, headers and serialized body have been prepared, immediately before **each actual provider fetch**, through `overdue_owner_attempt(queueId)`.
3. The database coalesces the original first initiated-attempt timestamp. A second device/retry never restamps it. The receipt means an attempt was initiated at that boundary; a crash can still occur between the receipt and network I/O. It proves neither provider acceptance, delivery nor a recipient read. The UI and personal notice say attempted / delivery unconfirmed.

Only after that original attempt plus ten minutes may the worker queue personal notices, and only within 24 hours of the saved overdue time. A missing arrival record is not proof of distress. The worker rechecks exact watch/contact revisions, ownership, source registration, enabled state, consent, capability and expiry immediately before every provider attempt. Concurrent revocation can still commit just after a provider accepts; atomic distributed recall is not claimed.

Personal delivery reuses 137-05's fixed Resend/Telegram transports, stored destinations, revocation HMAC, quota rows and retry policy. Email uses the same idempotency key and exact immutable prepared text across at most three attempts. Position age is explicitly referenced to immutable notice-preparedAt, so retries do not silently change that text as wall-clock minutes pass. Telegram reserves its one uncertain attempt before HTTP and does not automatically retry it.

## Caps and truthful capability

- Owner notice admission: ten per owner / 1000 globally per UTC day, distinct from safety push quotas. Personal provider attempts share 137-05's thirty per owner / 5000 globally per day. A due watch does not bypass those limits.
- Work is at most four pages of 16 watches and ten provider claims per invocation, a 12-second budget checked between bounded five-second HTTP calls, no redirects, 4 KiB incoming work body and 64 KiB fixed RPC responses. A persisted private cursor resumes unfinished sweeps, so a blocked first page does not permanently starve later vessels. Saturated/incomplete passes cannot certify a complete healthy run; this is not a worldwide throughput guarantee.
- Pending personal notices expire after ten minutes. Owner queues expire after ten minutes or the 24-hour overdue window, whichever comes first. Private delivery/dedupe rows and global quota rows are pruned after seven days. One current compact plan is retained per boat; there is no accumulating trip/route archive here.
- `private_overdue.control` defaults off with function_version 0, delivery_version 0 and no entitlement lease/worker health. Readiness requires explicit reviewed versions 1, an unexpired entitlement, the exact active one-minute cron command, and a complete healthy worker tick within five minutes. `delivery_version` is a **manual reviewed deployment proof**, not inferred from a key, SQL presence or an empty worker pass. Worker execution only maintains worker_at. New opt-ins are hidden until this capability exists; an existing watch remains stoppable when it is held.
- Status is owner/boat/clock bound. `watch.reviewRequired` exposes changed contact consent/revision or position registration, without adopting it. `ownerQueuedAt`, `ownerAttemptedAt`, `contactsQueuedAt` and `endedAt` remain separate original facts. Contacts queued is not contacts delivered. Satellite Mode makes no background or explicit cloud request; a cloud cancellation needs an online acknowledgement and is never claimed optimistically.

## Fixed sender integration — root review still required

The fixed queue data is exactly `{overdue_watch:1,boatId,revision,overdueAt,expiresAt}`. `utils/overdueWatch.ts` exports `parseOverdueNotice`, which refuses unknown fields, future due time, expired/overlong expiry and mismatched UUID shape. No plan, position or recipient details go into the owner lock-screen queue.

The intended APNs policy is ordinary active/default sound, no Critical or Time Sensitive override, no custom alarm/audio priority; thread `thalassa-overdue`, collapse `overdue:<revision>` (44 bytes), ten-minute TTL. Root owns the production sender/config/hook changes and the synthetic actual-index proof. This checkpoint does not alter those shared files. Existing anchor/AIS/radar priority remains intact.
