# Confirmed followed-route handoff

The Pi core uses Signal K's fixed v2 [Resources API](https://github.com/SignalK/signalk-server/blob/master/docs/develop/rest-api/resources_api.md) and [Course API](https://github.com/SignalK/signalk-server/blob/master/docs/develop/rest-api/course_api.md). It saves and reads back the exact followed line before activating its own generated UUID resource. Coordinates are not simplified, rounded or thinned. It does not call autopilot engagement, steering or Course API configuration endpoints.

A preview makes read requests only. The one-use confirmation lasts30 seconds and binds the device, route digest and previously observed course. Activation requires the skipper's pilot-in-standby check and refuses a reported engaged pilot. Changed authority, geometry, current course or an expired confirmation stops activation. A Pi-local operation guard serializes this writer's mutations.

Ownership is persisted before the uncertain activation request. A lost reply retains its claim for later reconciliation; it never triggers another automatic activation. Earlier ownership is retained through a failed replacement. At most eight uncertain claims are accepted, with strict fixed field bounds. Clearing matches the device, route key, generated resource and confirmed start time before issuing a course clear, then reads back the result. A different observed course is retained.

The stock Course API has no conditional compare-and-clear operation. Another helm can change its course between a GET and DELETE, so the preflight check is not an atomic lock against other Signal K clients. Clearing also does not silence an independent NMEA destination source; Signal K documents that such a source may repopulate navigation. These limitations need explicit helm context in the final interface, and must not be described as a guarantee that Thalassa controls the vessel's pilot.

The private ownership file is bounded to16KiB and tied to this Pi. Writes use a0600 exclusive temporary file, file fsync, atomic rename and directory fsync on Linux. A corrupt, oversized, symbolic-link or foreign-Pi receipt refuses an overwrite. No route coordinates or access tokens are stored in it.

Authority can be checked asynchronously against the current enrolled-device list between network operations. Unfollow invalidates an in-progress confirmation before waiting for the writer. If activation has already reached the server, clearing waits for that result and reconciles its retained claim; no activation request is replayed.

The four fixed `/api/course` endpoints are capability, preview, activate and clear. Every endpoint requires a currently enrolled device on the boat's own Wi-Fi, including while the legacy command lock observes or has no devices. A routed tailnet, router or loopback peer cannot claim helm access. Activation and clearing are command-class routes; preview only reads. No caller can supply a Signal K origin, access token or arbitrary API path.

Route sending defaults off. The operator must configure `SIGNALK_ACCESS_TOKEN` with approved write access and separately set `THALASSA_SIGNALK_COURSE_WRITES=1`; read access never turns this on. The token stays on the Pi. Fresh `steering.autopilot.state` values use the [Signal K steering schema](https://github.com/SignalK/specification/blob/master/schemas/groups/steering.json) and their own timestamps. An active mode blocks activation. Missing/stale state is explicitly unknown, requiring the skipper's direct standby confirmation rather than being labelled standby.

The Obs route menu opens a lazy “Send to plotter” confirmation for the exact followed line. It requires a pinned native connection, enrolled phone, unchanged account/pairing/base URL, unchanged followed geometry, the fresh one-use preview and explicit standby/replacement checks. A callback fences identity and intent again after asynchronous enrollment-header loading, immediately before native dispatch. Dense routes that exceed the1000-point/32KiB handoff are refused without removing points.

Before activation the phone synchronously saves a bounded, account-scoped receipt containing only the paired public identity and route key. No route coordinates, confirmation token, access token or provider credential are in that receipt. Uncertain sends retain it across restarts. The real Follow store asks to clear its previous sent route on unfollow, replacement or changed geometry; an account swap is separately fenced and cannot clear the old account using the new account's receipts. Missing connectivity retains the receipt and raises an explicit unconfirmed-clear message. The dialog also offers a deliberate recovery clear for this phone's receipts on the currently paired boat. There is no activation retry or WAN fallback.
