# Route worker stack fallback through exclusion audits

The new route-exclusion admission catches converted a genuine worker stack overflow into an ordinary `exclusion-unavailable` result. The worker host therefore kept that failed worker answer instead of rerunning the same job on the main thread. On the unchanged parent `49f32b5aac6d8ae7262fea7cd36fbb60b3db56f0`, the real-protocol worker suite reproduced both reported failures: 27 cases passed and two failed. The raw first result remains in `work/validation139-stack-fallback-baseline.log` outside the checkout.

The shared `isRouteStackOverflow` helper preserves the original exact classification: an actual `RangeError` whose message matches `/stack/i`. The new engine admission/final-audit catches and job final guidance catch rethrow only that compute failure to the existing outer job handler. Other range errors, ordinary errors mentioning a stack, malformed hard geometry and known forbidden crossings retain the existing refusal behavior. This helper grants no route, chart, depth or exclusion authority.

The outer job handler now explicitly clears `output.result` before returning a thrown-job failure. A candidate can already have been assigned when its final exclusion or traffic/coverage audit throws; that geometry is never an accepted answer. A genuine stack failure returns `result: null` and `outOfStack: true`. The existing host retries the original job on the main thread, recomputing the engine and all final audits. A non-stack failure does not obtain a worker-to-main retry through this change.
