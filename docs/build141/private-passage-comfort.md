# Private passage comfort

This is a personal preference beta, not measured wave truth, forecast accuracy or a safety rating. No yacht has fabricated calibration reports. The existing physical sea-comfort helper supplies the default; a qualified preference can move its word by at most one. Rough/very-rough WMO floors and independent routing limits still apply.

Each physical input needs at least six admitted reports across three different actual voyages. Each voyage contributes its median difference from the unchanged physical baseline; the median of those voyage medians is truncated toward zero and bounded to±1. Reports are tied to the current owned boat's exact type, length and profile revision. An edited parent capture remains privately listable/deletable but cannot calibrate. Profile changes/reset/lifecycle changes cannot borrow an old cohort.

The Vessel routing section opens a lazy private sheet with actual report, pending/delete and reset actions. Capture requires an explicit foreground action while that owned vessel is recording, an accepted original GPS fix no older than45seconds and a device-recorded point from the current voyage within five minutes and500metres. Auto/manual producers now stamp their genuine `device` source; the existing rolling device waypoint is also accepted. No old/source-null record or GPX import is relabelled. The model is requested at the actual retained capture point, independent of the Glass selection.

Qualification also requires the recording resolver's actual confirmed OCEAN/coastline evidence, exact-point unenclosed geometry and a local answering wave cell entirely inside the original coast-clearance circle after subtracting the moved-capture offset and100m spare. Missing geometry/model/cohort leaves the report unsaved with an explicit reason. These are source-admission checks on client-reported context, not server attestation of physical presence or observed sea height. GPS/model data and the subjective word remain self-reported.

Server storage is the separate non-exposed `private_comfort` schema with RLS and no client table grants or Realtime membership. The sole authenticated invoker RPC delegates to a strict private definer: actual `auth.sessions`, owned active unarchived boat, exact current profile/context/epoch and a joined actual owned uploaded `ship_logs` capture. No shared/public sighting/log DTO, export or row receives subjective fields. Owner deletion cascades the sidecar. Parent deletion cascades report payloads. Deleting a report physically removes its payload and retains only an operation tombstone to refuse late resurrection; reset rotates the epoch and clears both.

The canonical migration was created through Supabase CLI. No live application of this migration is claimed. A read-only schema metadata check confirmed the actual parent UUID/user/boat keys, text voyage/source/type/operation fields, timestamp and float8 coordinates before writing the adapter. The isolated fixture preserves those types and existing account-deletion fence.

Lock order uses the existing account advisory key (`hashtextextended(owner,20260806)`). RPCs do not take boat/profile row locks. Boat lifecycle already holds its boat row, then locks distinct old/new owners in sorted order, invalidates their context UUIDs and deletes the boat cohort in the same transaction. The cohort deliberately has no boat FK: an RPC holding the account advisory lock must not wait on a reverse boat FK key-share lock. Actual archive/restore, delete and owner A→B→A paths retire old reports/context. Final session/profile rechecks do not introduce profile-row locks. Queued old context/epoch writes refuse with40001 rather than rebind.

Bounds: at most120 report/deletion operation slots per boat,30 successful RPC calls/minute per owner (the counter survives vessel changes),50 owner-scoped encrypted pending operations for30days, four active private reads including orphaned reads, six-second client RPC waiter and a drain of at most eight operations/12seconds per ordinary log-sync round. Private server rows stay in RAM with a60second preference lease; only pending operations persist under a new encrypted owner-scoped key. Auth/vessel/profile/reset changes retire RAM synchronously. No automatic public sharing, telemetry or background location collection is added.

A report needs a current server cohort and actual qualifying source data when captured; this does not promise offline unqualified capture. It queues privately without forcing upload of an active voyage. The existing ordinary log sync later uploads the parent, then attempts its private sidecar. Parent-not-uploaded23503 stays pending. Actual parent deletion intent is reused; a missing deletion ledger refuses retry, rather than deleting a valid pending report. Stale context/epoch and account tombstones cannot resurrect queued data. Account deletion purges the encrypted pending key as well as server cascades.

Development proof:58 assertions against the canonical migration in PGlite,28 strict disposable-target guard tests,72 capture/qualification/real-producer cases and scoped lint0. PGlite is WASM development evidence, not actual PostgreSQL concurrency. The prepared Linux PostgreSQL17.6 adapter runs the same canonical SQL plus nine races, each observing the exact gate PID through `pg_blocking_pids`: duplicate save, save/delete, save/reset, profile edit, session revocation, account tombstone, final slot, archive/restore and transfer A→B→A. Actual Linux proof is required before live application.
