## User path and honest evidence

The existing model picker scroll contains a lazy, initially collapsed **Private boat scorecard**. Merely mounting or expanding it performs no Pi or provider request. Its transport adapter loads on the first explicit review/read action. The normal browser keyboard suite includes `own-boat-skill141-layout.spec.ts`.

Review requires an authenticated selected owned vessel, the enrolled phone, native pinned transport and boat-LAN admission. The user confirms the actual selected vessel/instrument association; a paired Pi or Signal K self identifier alone does not establish that association. Logging has its own initially unchecked choice. An older Pi remains unavailable; this source is intended for the separately reviewed Pi update 9.

Advice uses two weeks of private true-wind observations and own-server forecasts captured before the measured time and valid hour. It compares the same observed hours in the exact same 0.25-degree forecast cell, independently for four issuer-lead bins. It never borrows IFS 0.25-degree scores for IFS 9 km, or invents a common issue clock for mixed GFS source runs. At least two comparable models, 30 conservative effective paired hours and a ten-day span are required. Warming means null MAE and no closest model. No model preference, route, watch, alarm, correction weight or public station truth is changed.

This is agreement with the reviewed instruments, not a calibrated standard 10 m wind observation. Height, shelter, calibration and motion may differ. Direct dated true-wind and GPS leaves are required; apparent wind, parent/receipt timestamps, held positions and the phone supplement cannot qualify. The ordinary local feed is not independent hardware attestation: the skipper must identify its actual source. No measured rain/wave truth is supplied by this feed, so those private scores remain unavailable.

## Separate owner authority and explicit activation

`SkillOwnerVerifier` uses only the configured startup-owned trusted Supabase origin. It verifies the live JWT at `/auth/v1/user`, then the actual `get_owned_vessel_fleet` result. The requested durable `boats.id`, current positive revision, matching owner and explicit non-archived/non-released state must be present exactly once. Caller-selected origins, a chart enrollment token or a self-asserted vessel UUID never prove ownership. JWTs are not stored or logged.

The binding includes owner, vessel and revision, Pi, enrolled controller and revision, registered pairing revision, self identity, true-wind source and position source. Review nonce: **60 seconds**. Owner-confirmation whole-operation monotonic ceiling: **10 seconds**, with the existing owner HTTP bound of eight seconds. Native Pi read timeout: **12 seconds**; phone transaction waiter: **20 seconds**. No late owner verification can mint a logging grant after its server admission deadline.

Confirmation installs a fresh opaque 256-bit capability **with logging OFF**. The server separately retains whether logging was explicitly approved. The phone must persist the exact returned capability before sending `/enable`; the Pi requires that capability, the original controller, current binding and logging-approved intent. Thus a lost confirmation response leaves logging OFF. A lost enable response leaves a stored stop capability. Read-only confirmation cannot enable logging.

Original consent/capability expiry: **14 days**. In-memory read session: at most **15 minutes**, capped by original consent expiry. Issue/renewal requires fresh owner verification; a current capability may read over pinned boat LAN while offline. Read receipt times never renew consent or evidence clocks. The Pi retains only the capability hash. The phone retains its opaque capability in the original owner and pinned-Pi namespace; it never stores the JWT there.

Wall rollback, monotonic expiry, OFF, controller/source/pair/account changes, generation replacement and A/B/A transitions fence late reads and writes. Actual enrollment/source context is re-read after forecast awaits before retaining a capture. Pending native transports remain charged across retired/remounted phone reviews until the actual promises settle, with at most two. Server owner/public readers similarly retain actual unsettled transport/body charges and cancel late originals.

**Stop** and **Stop and clear** require no WAN or fresh JWT. An expired stored capability can still stop its original logger; a changed vessel revision cannot strand that privacy stop. An unconfirmed stop retains the original capability for retry. An open adapter attempts an original-Pi stop on account retirement, even if local storage removal fails. The global auth hook only removes this one previous-owner key; it imports no Pi/provider module and sends no request. Closing the ordinary review or backgrounding the phone retires reading, while separately approved logging can continue.

An offline Pi cannot learn a remote logout, deletion or pairing change it has not received. Its local logging may continue until observed retirement or the original 14-day expiry. The consent UI states this limitation and directs the skipper to stop/clear on boat Wi-Fi before disconnecting. This process-local capability is not exported as public or cloud authority.

## Private retention and runtime integration

New routes live only under `/api/own-boat-skill` and the existing application-API boundary. Every route independently requires boat LAN and current chart-device enrollment, sends no-store headers, and uses the existing command-lock table. Enrollment is transport authority only. The small private JSON parser runs after those guards, refuses already-parsed/compressed/query-overridden bodies and caps original request bytes at 16 KiB. Private response bytes are capped at 128 KiB. Capabilities are body values, never query strings.

The server uses existing registered relay identity only as pairing context. No new relay, worker, public bucket, schema, UDP sender or cloud upload is introduced. Default OFF performs no private acquisition or database creation. Explicit logging resumes after a Pi restart only within its original durable consent and source fences. Internet policy OFF preserves local instrument logging while preventing new forecast reads.

The SQLite ledger is separate at `CACHE_DIR/own-boat-skill/private-skill.sqlite`, directory 0700/file 0600, checked application/schema identity, secure-delete, FULL synchronous transactions and DELETE journal. It retains at most 337 hourly measured samples, 1,024 immutable issued forecast originals and 32 MiB of original forecast bytes. Fixed 4 KiB pages and 9,216 maximum pages cap the database at 36 MiB (up to another database-sized rollback journal during a transaction). A durable once-per-UTC-hour claim admits at most six fixed own-server model reads; retries, movement, replacement and clear do not reset that acquisition budget. Original raw SHA and small derived metadata proof are checked while streaming stored issues; the read result does not retain the entire raw footprint.

Samples retain the original selected scalar true-wind leaf, timestamps, wind value and a coarse forecast cell. The private scorecard retains no exact GPS track. Renewing the same association keeps the bounded window; explicitly replacing an association clears prior scorecard evidence atomically. Clear is logical database evidence removal, not a claim of forensic disk erasure. Existing tracks, scientific correction jobs, public buoy data and other private features are separate.
